#+title: GNU Emacs Configuration
#+author: GinShio

一份以文學編程維護的 Vanilla Emacs 配置。=config.org= 與 =org/*.org= 是 Ginshio 配置
模塊的唯一真實來源；它們生成 =modules/ginshio/*.el=。受版本控制的 =early-init.el= 與
=init.el= 只是 fail-closed loader，不是生成物。=modules/= 的其他子目錄保存受版本控制的
上游 Lisp 與外部資產。

* 契約

- 支持 Emacs 30.1 或更新版本。
- =XDG_CONFIG_HOME=、=XDG_DATA_HOME=、=XDG_STATE_HOME=、=XDG_CACHE_HOME= 與
  =XDG_RUNTIME_DIR= 必須存在於環境中，而且必須是絕對路徑。
- =XDG_RUNTIME_DIR= 必須已存在、可寫，且權限是 =0700=。
- 正常 Emacs 啓動只激活已安裝、已構建、已鎖定的套件；不下載、不更新、不修復。
- 配置或套件缺失時直接中止啓動。不隔離失敗模塊，不建立 safe mode。
- 套件下載、更新、構建與 lock file 全部由 =bin/ginshio-emacs= 的獨立批處理進程完成。
- 那個進程不載入配置。它把 =modules/ginshio/*.el= 當作資料讀取，取出其中的
  ~:straight~ 宣告；配置代碼一行都不執行，所以寫壞的 ~:config~ 擋不住裝包。

* 第一次安裝

#+begin_src shell
bin/ginshio-emacs sync
#+end_src

=sync= 會 tangle 配置，讀出宣告，依據 =straight.lock= 記錄的 commit 安裝、構建並生成
activation 快照；新增宣告追加 pin、移除的宣告會從 lock 與套件樹清掉，既有 pin 不動。
首次沒有 lock file 時會從當前 recipes 建立第一份；只有 =upgrade= 才把仍在使用的 repo
全量改鎖到新 revision。

套件 source 與 build 都在：

#+begin_example
$XDG_DATA_HOME/emacs/straight/
#+end_example

由 straight 管理。構建目錄與 activation 快照都按 Emacs 版本分家（=build-30.2/=、
=activation-30.2.elc=），clone 與鎖則由所有版本共用：換一個 Emacs 版本只需要再跑一次
=sync=，不重新下載，而且換回去不用重建。

* 控制命令

| 命令                         | 用途                                                      |
|------------------------------+-----------------------------------------------------------|
| =bin/ginshio-emacs sync=       | 按 lock 安裝缺的包並構建；既有 pin 不動                   |
| =bin/ginshio-emacs upgrade=    | 更新上游、重建動過的包、把新 revision 寫回 lock           |
| =bin/ginshio-emacs rebuild=    | 按 lock 重新構建每一個包，並規範化每個倉庫的 remote 與分支 |
| =bin/ginshio-emacs clean=      | 刪 tangle 產物、構建、快照與 eln cache；保留 clone        |
| =bin/ginshio-emacs cleanall=   | 再加上 clone                                              |
| =bin/ginshio-emacs doctor=     | 載入完整配置並檢查外部程序、字體、grammar 與目錄          |

*=sync= 在無事可做時完全不聯網。* 它先比對每個倉庫的 HEAD 與鎖，只有真的對不上纔切換
revision。所有東西都已就位時，一次 =sync= 是純本地操作，大約三秒。

=rebuild= 補的是一個 =sync= 看不見的狀態。配置關掉了 straight 的修改偵測（理由見
=05-packages.org=），所以 straight 從不自己判斷某個 build 過期；一次被打斷的 =sync=，
會留下一棵「已構建」但缺檔案的樹，而 =sync= 會信任它。=sync= 也只重建 revision 真的動
過的包，所以「依賴改了一個宏、內聯了它的包卻沒重建」這類殘餘同樣由 =rebuild= 收尾。
recipe 本身改了不需要它——那會自動觸發重建；*換過 Emacs 版本也不需要*，構建按版本分家。

=clean= 與 =cleanall= 的差別是要不要重新下載。=clean= 刪 =modules/ginshio/=、
=$XDG_DATA_HOME/emacs/straight/build*=、=$XDG_DATA_HOME/emacs/activation*= 與
=$XDG_CACHE_HOME/emacs/eln-cache/=，保留 =straight/repos/=，所以之後的 =sync= 不需要
網路就能恢復。=cleanall= 連 =repos/= 一起刪，恢復要重新 clone。

兩者都保留 =early-init.el=、=init.el=、=config.org=、=org/*.org=、=tangle.el=、
=maintain.el=、=straight.lock=、=modules/= 下受版本控制的 source 與資產、tree-sitter
grammars 與其他使用者資料；auto-save 和 backup cache 也不受影響。清理後普通 Emacs 必須
啓動失敗，直到再次運行 =sync=。執行前應先由 system/service 停止所有使用這份配置的
Emacs；腳本不探測或管理 daemon。

普通會話不載入 straight；套件管理命令只存在於 =maintain.el= 裏。需要查看或改動套件樹時
退出編輯流程，用上面的命令處理。

* Server

配置同時兼容普通圖形 Emacs、默認 daemon 與具名 daemon；=bin/ginshio-emacs= 不負責它們的啓停。
daemon 的進程生命週期應由 system/service 維護，客戶端直接使用 Emacs 原生的
=emacsclient=。

日常路徑保持 Emacs 的默認 server 名 =server=。普通圖形 Emacs 啓動後會自動開 server；
默認 daemon service 的底層命令可直接使用 Emacs 的前臺 daemon 模式：

#+begin_src shell
emacs --init-directory=/path/to/emacs-next --fg-daemon
emacsclient -c
#+end_src

只有需要隔離第二個 daemon 時才使用原生具名 server：

#+begin_src shell
emacs --init-directory=/path/to/emacs-next --fg-daemon=work
emacsclient -s work -c
GINSHIO_SERVER_NAME=scratch emacs --init-directory=/path/to/emacs-next
#+end_src

daemon 名由 ~--daemon=NAME~ / ~--fg-daemon=NAME~ 帶入；=GINSHIO_SERVER_NAME= 只用於讓普通
圖形 Emacs 顯式成為另一個具名 server。不設名字就是唯一的默認 server。Unix socket 由
Emacs 放在 =$XDG_RUNTIME_DIR/emacs=，配置不啓用 TCP server，也不設 =server-auth-dir=。

* 使用文檔

=GUIDE.org= 是面向使用的入口：工作流、鍵位、功能發現、各包手冊與常見操作都集中在那裏。

在 Emacs 裏：

| 鍵         | 用途                           |
|------------+--------------------------------|
| ~M-m~        | 打開 leader；停一下看 which-key |
| ~M-m f g~    | 打開 =GUIDE.org=                 |
| ~M-m f p~    | 打開文學配置源碼                 |
| ~M-m h m~    | 查看當前 major/minor mode 的說明 |
| ~M-m h k~    | 查看一個鍵實際執行什麼           |
| ~M-m h f~    | 查看一個函數                     |
| ~M-m h v~    | 查看一個變量                     |
| ~M-m h b~    | 列出當前緩衝區全部有效鍵位       |

這份配置只重置全域 keymap；major mode 的 =C-c= 鍵與 mode-local map 完整保留。因此引入一個
包之後，第一個動作應該是 ~M-m h m~，而不是只看 leader 表。

* 結構

=tangle.el= 自動發現全部 =org/NN-name.org=，按完整文件名字典序 include。功能模塊從文件名
得到 =name=，生成 =modules/ginshio/ginshio-name.el=，同一順序也直接生成 ~ginshio-modules~；不存在
另一份要同步修改的 manifest。

=modules/ginshio/= 是唯一可由 tangle 與 =clean= 整體重建的 Lisp 子樹。其他
=modules/NAME/= 目錄是受版本控制的上游 Lisp 或外部資產；啓用它們的配置模塊只把自己
需要的精確目錄加入 ~load-path~，不遞迴暴露整棵 =modules/=。

每個文件第一行用 =#+GINSHIO_MODULE:= 聲明自己的狀態：

| 值           | tangle | 加入 ~ginshio-modules~ |
|--------------+--------+------------------------|
| =bootstrap=    | 是     | 否                     |
| =support=      | 是     | 否                     |
| =enabled=      | 是     | 是                     |
| =disabled=     | 否     | 否                     |

新增功能模塊只需建立 =org/NN-name.org=、寫上 =enabled=，並讓它生成及提供
=modules/ginshio/ginshio-name.el= / ~ginshio-name~。=NN= 不必連續；它和後面的 =name= 共同決定加載
順序。停用時只把該文件改為 =disabled=；成功 tangle 會刪除殘留產物，因此其他啓用模塊若
仍 ~require~ 它，完整啓動會直接失敗而不是暗中重新啓用。

改動之後的完整檢查是一條命令：

#+begin_src shell
bin/ginshio-emacs sync && bin/ginshio-emacs doctor
#+end_src

=sync= 一共起三個進程：tangle（其中會驗證每個生成檔的括號與可讀性）、maintain（讀出宣告、
按 lock 安裝與構建、寫鎖與快照）、validate。最後那個從零開始，像普通會話一樣只消費快照，
再逐個 ~require~ 每個宣告的 feature——延遲加載的 ~:config~ 因此仍然被執行過一次。任何一
步失敗都以非零退出碼結束。

~:straight~ 的宣告必須是字面量，而且 ~use-package~ 必須寫在文件頂層。=maintain.el= 讀不
動的東西會直接報錯並指出是哪個文件的哪個包，不會默默跳過。
